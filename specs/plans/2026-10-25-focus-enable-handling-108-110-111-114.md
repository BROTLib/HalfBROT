# Focus drive enable: one owner, no lock while a move or homing is wanted (#108, #110, #111, #114)

**Status: proposed. Nothing implemented, compiled, or run on a PLC or a telescope.** Facts below were read on
2026-10-25 from HalfBROT `develop` @ `918f0d5` (0.7.2), BROTLib `develop` @ `f23505d` (plcproj 0.10.4 plus the
unreleased step 4.1, `034ce29`/`058c4eb`), MONETcommon `develop` @ `2bbda83` (0.9.9), MONETS `develop` @ `9775aa7`
(1.4.5; pin PR MONETS#56 @ `3a3e9b8` open), MONETN `develop` @ `5dd90dd` (1.4.5; pin PR MONETN#42 @ `9af9f0f` open),
IAG50cm `ci/pin-brotlib-0.10.4` @ `6dc1037`. Line numbers are those files at those commits (file lines, not
`LineIds`). Anything marked **hypothesis** is not confirmed by the code or a log.

Issues: **#111** (deadlock after a homing), **#108** (queued `MoveTo()` never starts, starts later by itself),
**#110** (brake timer drops the enable as a move starts, 0x4260), **#114** (stop during a manual re-home, 0x4260).
Decided **out of scope** (section 7): #103, #85, #102, MONETcommon#122, BROTLib#74.

**One plan for four issues.** All four are the same defect: `FB_FocusControl` writes `bEnable` in four places
(`:146`, `:150`, `:231`, `:259`, plus `:188`), none of them asks whether a move or homing is starting, pending or still
decelerating, and the follower decides "ready" from an `fbAxis.Ready` that is one cycle old. They go into the same
block, the same release, the same tests and the same on-site session. Each part below is its own commit so it can be
reverted alone.

## 1. Problem

### 1.1 Common facts (verified in the code)

- `FB_FocusControl.TcPOU:90`: `ObFocusUnlock := (bManualUnlock OR bEnable) AND NOT bError` (brake release output),
  `:93` `tonFocusDelay` gives `bFocusUnlocked` after `ptFocusDelay` (MONETS `MAIN.TcPOU:159`: 100 ms; default 500 ms),
  `:212` `fbAxis(enable := bFocusUnlocked)`. So a `bEnable` written in cycle k reaches the drive in the `fbAxis`
  call of cycle k+1 (off: at once, `TON.Q` drops with `IN`; on: after `ptFocusDelay`).
- `:102-112` the follower runs **before** the `fbAxis` call with `bReady := fbAxis.Ready`, i.e. the `Ready` of the
  last call, which was made with the last cycle's enable.
- BROTLib `FB_Axis.TcPOU:123-129` `Ready` is `MC_Power.Status`; `:216-218` `MoveCommand(Allowed := Ready AND
  Calibrated AND NOT ExtActive)`; `MoveTo()` (`:378-380`) only latches a request. `FB_AxisCommand.TcPOU:40-46`: a
  request waits while not `Allowed`, and if `Execute` is still TRUE from the last command it is held low for one
  cycle first (`:42`). So a `MoveTo()` on a disabled drive stays `MovePending` until the drive is enabled, by anyone,
  and then runs.
- BROTLib `FB_MoveFollower.TcPOU:49-67`: `bNeedEnable` is set only in the `NOT bMoving` branch (`:58-65`, off target
  and `NOT bReady`). Once `bMoving` is TRUE (`:52-57`) it never asks for the enable. `bMoving` is set together with
  `bStartMove` (`:59-62`) and only cleared by `MoveDone`, error, `StopDone`, abort (`:39-41`), `NOT bActive` (`:49-50`)
  or `Stop()` (`:75-78`). History: `a534b6c` (2026-10-21, MONETcommon#122).
- The writes of `bEnable` in `FB_FocusControl` (blame): `:145-147` `bNeedEnable -> TRUE` (`0de89bc`, 0.6.0),
  `:149-151` brake delay `-> FALSE` (`36beb09`/`26c8c71`), `:188` accepted manual re-home `-> TRUE` (`36beb09`),
  `:230-231` `rtHomed -> FALSE` (`9eb0181`, #80), `:258-259` aborted re-home, uncalibrated `-> FALSE` (`36beb09`).
  Outside: pendant `FB_MonetPendantControl.TcPOU:116` (`Enable := IbEnableButton`, selection 5), power-on stage 10
  `FB_MonetTelescopeControl.TcPOU:1114-1120` (`fbFocus.Enable := TRUE` while uncalibrated).
- `:95` `tonBrakeDelay(IN := NOT fbAxis.Busy AND fbAxis.StandStill)` runs in every mode and state, from the last
  call's outputs; it is only acted on inside `IF automatic AND NOT bManualUnlock` / `IF calibrated` (`:139-151`).
- Inferred, not verified on the NC: a disabled axis does not report `StandStill` (PLCopen state *Disabled*), so
  `tonBrakeDelay` restarts after every lock. Evidence: BROTLib#74 shows a locked focus enabling itself and moving
  0.3 s after a new target; if `StandStill` stayed TRUE while disabled, `:150` would clear the `:146` enable in the
  same cycle and no move after a lock could ever start.

### 1.2 #111: deadlock after every homing (verified, matches all three reports)

Cycle N is the first cycle in which `fbAxis` reports `HomeDone` TRUE and `HomeActive` FALSE (end of a cam homing).

| Cycle | Line | What happens |
|---|---|---|
| N | `:102` | follower inactive (`bActive` needs `NOT bHomeAxis`) |
| N | `:204-206` | `fPosition := fHomingPosition` (92.02, cam homing) |
| N | `:211` | `fbAxis` with enable TRUE: `Ready` TRUE, `HomeDone` TRUE, `HomeActive` FALSE |
| N | `:229-231` | `rtHomed.Q`: **`bEnable := FALSE`** |
| N | `:241-243` | `F_FocusHomeRelease` TRUE: `bHomeAxis := FALSE` (same cycle as `rtHomed`, same condition) |
| N | `:251-253` | manual re-home only: `bDone`, `fPosition := fRestoreTarget` (36 in the second #111 report) |
| N+1 | `:87` | clamp: 92.02 -> `fMaxPosition` 91.5 (MONETS `MAIN.TcPOU:156`); 36 stays 36 |
| N+1 | `:90-93` | `ObFocusUnlock` FALSE, `bFocusUnlocked` FALSE |
| N+1 | `:102-112` | follower active, `bReady` = `Ready` of cycle N = **TRUE**, `|91.5 - 91.993| > 0.005`: `bStartMove`, `bMoving` TRUE |
| N+1 | `:142-147` | `fbAxis.MoveTo()`; `bNeedEnable` FALSE (it was ready) |
| N+1 | `:211` | `fbAxis(enable := FALSE)`: `Ready` FALSE, `MoveCommand` not allowed: `MovePending` TRUE |
| N+2.. | | follower in the `bMoving` branch: no `bNeedEnable`, no writer of `bEnable`: stuck |

This is exactly the observed state (`MovePending` TRUE, `bMoving` TRUE, `bNeedEnable` FALSE, `bEnable` FALSE,
`ObFocusUnlock` FALSE). A new MQTT target restarts via `:53-56` (`bStartMove`, another `MoveTo()`), still pending:
the third report ("`focus=36` changes the target but the move stays queued"). The second report (manual re-home,
restore target 36) shows that the clamp is not needed for the deadlock: any target off the actual position after
a homing deadlocks.

**Correction to the earlier finding 3.** "On `rtHomed` set `fPosition := fActualPosition`" alone does not help on
MONET/S and MONET/N: the next scan's clamp (`:87`) turns 91.993 into 91.5 again, the same target as today. The cam
edge (91.993) is outside the allowed range (0.5..91.5, MONETcommon#122: 0.5 mm inside the switches at 0 and 92.02),
so after every cam homing the focus **has** to move 0.49 mm down off the far switch, or stay on it. What has to be
fixed is that this move can run; the explicit target is a clarity change (section 2.3 C, Q1).

### 1.3 #108: a pending move with a locked drive (verified for the mechanism, the initial state is a hypothesis)

- Observation 2/3 (`focus=64`, 60 s nothing, `bMoving` TRUE, `bNeedEnable` FALSE, `Ready` FALSE, `MovePending`
  TRUE; `bEnable := TRUE` by hand starts it at once) is the state of 1.2 and follows from `FB_MoveFollower.TcPOU:52-57`
  and `FB_AxisCommand.TcPOU:40-46`.
- How the focus got there before any homing (observation 1, locked 0.008 mm off target with a pending move):
  **hypothesis**, the race of 1.4: the brake delay fires in the cycle the follower restarts after a `MoveDone` 0.008
  mm off (hunting, #85); the restart hits the one-cycle low of `FB_AxisCommand.TcPOU:42`, so the request is still
  pending when the enable drops one cycle later.
- "Starts by itself later" (observation 4, and survives power-off/on): the pending request is never dropped while
  the follower is inactive. `bManualUnlock` (`:90`) enables the drive without the follower (`:106` inactive), and the
  stale `MoveCommand` runs because `Allowed` only checks `Ready AND Calibrated`. Nothing in `FB_FocusControl` calls
  `fbAxis.CancelMove()` except `Stop()` (`:410`). An error ends `bMoving` (`FB_MoveFollower.TcPOU:39`) but does not
  cancel the request; `Reset` does (`FB_AxisCommand.TcPOU:36-39`).

### 1.4 #110: the brake delay drops the enable in the cycle a move starts (verified)

The reported sequence, cycle M = first cycle after `bManualUnlock := FALSE` (with `bEnable` TRUE written before):

| Cycle | Line | What happens |
|---|---|---|
| < M | `:95` | `tonBrakeDelay` has run for 65 s (`IN` does not look at mode or `bManualUnlock`): `Q` TRUE |
| M | `:102` | follower active, `bReady` TRUE, off target: `bStartMove` |
| M | `:143` | `MoveTo()` |
| M | `:149-150` | `tonBrakeDelay.Q AND NOT bHomeAxis`: **`bEnable := FALSE`** in the same cycle |
| M | `:211` | enable still TRUE (from `:93`): `MoveCommand` executes, `MC_MoveAbsolute` starts |
| M+1 | `:90-93`, `:211` | enable FALSE while the move executes: NC 0x4260, emergency park |

`tonBrakeDelay` is computed from the last call's `Busy`/`StandStill` and nothing resets it on `bStartMove`, so a move
started in the cycle `Q` is TRUE is disabled in the next. In pure automatic operation `Q` is TRUE only for the one or
two cycles before the lock takes effect (then the drive is disabled and, per 1.1, not `StandStill`), so the window is
a target arriving in exactly the cycle `ptBrakeDelay` expires (rare, not reproducible by hand). It is wide open
whenever the automatic branch was not evaluated while the enabled focus stood still: `bManualUnlock` (the report),
manual mode with the pendant enable held, or an uncalibrated phase. If `Execute` was still TRUE from an older
command (`FB_AxisCommand.TcPOU:42`), the same race gives the #108 state instead of 0x4260.

### 1.5 #114: stop during a manual re-home (hypothesis, two candidates)

Verified parts: `stop=1` reaches `fbFocus.Stop()` once per stop (`FB_MonetTelescopeControl.TcPOU:1882-1886`).
`FB_FocusControl.Stop()` (`:409-419`): follower `Stop()`, `CancelMove()`, `CancelHome()` (only a pending one), and
because the homing axis is `Ready AND NOT StandStill`, `fbAxis.Stop()` (MC_Stop; `FB_Axis.TcPOU:265-272` allows it
while `Homing`). `fPosition` back to 36 is explained by the emergency park after the error: park stage 0 writes
`fbFocus.Position := focusPark` (`FB_MonetTelescopeControl.TcPOU:943`, MONETS `MAIN.TcPOU:42` `focusPark := 36.0`).

- **H1, enable dropped while MC_Stop decelerates.** MC_Stop aborts MC_Home: `Axis_Home.CommandAborted`,
  `FB_AxisCommand.TcPOU:47-48` releases `Execute`, `HomeActive := Execute OR Busy` (`FB_Axis.TcPOU:253`) drops while
  the axis is still `Stopping`. `FB_FocusManualHome.TcPOU:35-41` ends with `bAborted` (abort pulse seen),
  `FB_FocusControl.TcPOU:256-259` sets `HomeAxis := FALSE` and, uncalibrated, **`bEnable := FALSE`**; the next cycle
  disables the drive during MC_Stop: 0x4260. Fits the mechanism and the 0x4260 text of #110 ("lost its controller
  enable while executing a command"). **Conflicts** with the report: after H1 `bEnable` would be FALSE and
  `bBlockAutoHome` TRUE, the report has `bEnable` TRUE and `bBlockAutoHome` FALSE.
- **H2, the error comes first, from something other than `bEnable`.** If MC_Home or MC_Stop reports an error before
  the homing is seen ending, `FB_AxisCommand` keeps `Execute` on an error (`:47` only releases on Done/Aborted), so
  `HomeActive` stays TRUE, `fbManualHome.bRunning` never ends (no abort branch: `bBlockAutoHome` FALSE, `bEnable`
  stays TRUE, as reported), and `F_FocusHomeRelease` releases `bHomeAxis` on `bError`. Candidates for the lost
  enable: drive side (EL7342 warning noted in #110), or the far-switch bypass `MC_SetAcceptBlockedDriveSignal(enable
  := bHomeAxis)` (`:209`) being released while the axis decelerates. Not verifiable from the code.
- **Inconsistent observation:** the report has `bError` TRUE and `ObFocusUnlock` TRUE at the same time, which
  `:90` cannot produce at the end of a cycle. Either the flags were read at different moments, or `bError` toggles.
  A per-cycle trace is needed (section 5, step 7) before the root cause of #114 is called fixed.

The fix below removes H1 (no lock before `StandStill`). It does not remove H2; Q4 proposes the optional bypass hold.

## 2. Change

Two repositories. BROTLib: a contract fix in `FB_MoveFollower` (independent, not required by HalfBROT). HalfBROT:
one pure-logic block that decides the enable, `FB_FocusControl` rewired to write `bEnable` only from it. No new
`VAR_INPUT`/`VAR_OUTPUT` on `FB_FocusControl`, no consumer code change.

### 2.1 BROTLib: `FB_MoveFollower` asks for the enable of a pending move (one PR to BROTLib `develop`)

`FB_MoveFollower.TcPOU:52-57`, in the `bMoving` branch:

```
	IF bMoving THEN
		IF ABS(fTarget - fMoveTarget) > fTolerance THEN
			bStartMove := TRUE;
			bRestarted := TRUE;
			fMoveTarget := fTarget;
		END_IF
		// a started move waits for the drive (FB_Axis.MoveTo() is pending while not Ready): ask for the enable (HalfBROT#108)
		bNeedEnable := NOT bReady;
```

Doc of `bNeedEnable` (`:25`): "a move is wanted (off target, or started and waiting), but the axis is not ready: the
caller enables it". No interface change. IAG50cm ignores `bNeedEnable` (`IAG50cm/POUs/FB_FocusControl.TcPOU:26`), so it
is unaffected. HalfBROT does not rely on this (2.2 already counts `bMoving`), it makes the documented contract true
for any caller.

### 2.2 HalfBROT: new pure-logic `FB_FocusDriveEnable` (`POUs/`)

In the pattern of `FB_FocusManualHome` / `FB_FocusJogLatch` (no NC access, the caller writes `bEnable`):

```
// Decides the drive enable of the focus (FB_FocusControl.bEnable) in one place, once per cycle after the follower and
// before ObFocusUnlock. On while a move or a homing is wanted (automatic positioning only). Off only when nothing is
// wanted and the axis is at rest (StandStill, not Busy): after the brake delay in automatic positioning, or at once on
// a lock request (end of a homing, aborted re-home), never while a move starts, waits or decelerates (#108, #110,
// #111, #114). Pure logic, tested without an NC axis.
FUNCTION_BLOCK FB_FocusDriveEnable
VAR_INPUT
	bAutomatic		: BOOL;		// automatic positioning: eTelescopeMode = automatic AND NOT bManualUnlock
	bCalibrated		: BOOL;		// fbAxis.calibrated
	bError			: BOOL;
	bMoveWanted		: BOOL;		// fbFollower.bNeedEnable OR fbFollower.bMoving OR fbAxis.MovePending (this cycle)
	bHomeWanted		: BOOL;		// bHomeAxis OR fbAxis.HomeActive OR fbAxis.HomePending
	bAtRest			: BOOL;		// fbAxis.StandStill AND NOT fbAxis.Busy, from its last call
	tBrakeDelay		: TIME;		// ptBrakeDelay
END_VAR
VAR_OUTPUT
	bEnableOn		: BOOL;		// this cycle: bEnable := TRUE
	bEnableOff		: BOOL;		// this cycle: bEnable := FALSE
	bLockPending	: BOOL;		// a lock request waits until the axis is at rest
END_VAR
VAR
	tonRest			: TON;		// at rest with nothing wanted (replaces FB_FocusControl.tonBrakeDelay)
	bWanted			: BOOL;
END_VAR

bWanted := bMoveWanted OR bHomeWanted;
tonRest(IN := bAtRest AND NOT bWanted, PT := tBrakeDelay);
IF bWanted THEN
	bLockPending := FALSE;		// a move or homing takes over; the brake delay locks after it
END_IF
bEnableOn := bAutomatic AND NOT bError AND bWanted;
bEnableOff := NOT bWanted AND (
		(bLockPending AND (bAtRest OR bError))		// bError: the drive is already off (ObFocusUnlock)
		OR (bAutomatic AND bCalibrated AND tonRest.Q));
IF bEnableOff THEN
	bLockPending := FALSE;
END_IF
```

Method `RequestLock()`: `bLockPending := TRUE;` (called at the end of a homing and on an aborted, uncalibrated
re-home; it takes effect in the next cycle's call).

`bEnableOn` and `bEnableOff` exclude each other (`bWanted`). The brake-delay lock keeps today's scope (automatic
positioning, calibrated; prior plan Q5 unchanged). `bHomeWanted` in `bEnableOn` makes an accepted re-home and the
automatic homing self-sufficient in automatic; MONETcommon's power-on (`:1116`) still sets `Enable` itself.

### 2.3 HalfBROT `FB_FocusControl` (one PR to HalfBROT `develop`, commits A-C, D optional)

**Commit A: one owner of `bEnable`, decided before `ObFocusUnlock`.**

`VAR`: `fbDriveEnable : FB_FocusDriveEnable;	// the only writer of bEnable in this block`. Remove `tonBrakeDelay`
(`:36`, `:95`).

Body order (from `:84`): `_MigrateLastPosition`, clamp (`:87`), then the jog latch and follower (moved up from
`:97-112`, so their results are known before the enable is decided; their inputs are last-call values and the
clamped `fPosition`, as now), with

```
	bReady		:= fbAxis.Ready AND bFocusUnlocked AND bEnable,	// the enable the last fbAxis call got, and not being dropped
```

(`bFocusUnlocked` is now the previous cycle's `tonFocusDelay.Q`, because `:93` moves below.) Then:

```
// a pending MoveTo() exists only for a move the follower runs: a stale one must not start when the drive is enabled
// for another reason (bManualUnlock, pendant, homing) or after a power cycle or error (#108)
IF fbAxis.MovePending AND NOT fbFollower.bMoving THEN
	fbAxis.CancelMove();
END_IF

// the only place this block writes bEnable (#108, #110, #111, #114); the pendant and the power-on still write Enable
fbDriveEnable(
	bAutomatic	:= eTelescopeMode = E_TelescopeMode.automatic AND NOT bManualUnlock,
	bCalibrated	:= fbAxis.calibrated,
	bError		:= bError,
	bMoveWanted	:= fbFollower.bNeedEnable OR fbFollower.bMoving OR fbAxis.MovePending,
	bHomeWanted	:= bHomeAxis OR fbAxis.HomeActive OR fbAxis.HomePending,
	bAtRest		:= fbAxis.StandStill AND NOT fbAxis.Busy,
	tBrakeDelay	:= ptBrakeDelay);
IF fbDriveEnable.bEnableOn THEN
	bEnable := TRUE;
ELSIF fbDriveEnable.bEnableOff THEN
	bEnable := FALSE;
END_IF
```

then `:90` `ObFocusUnlock`, `:93` `tonFocusDelay`, and the rest unchanged. Remove `:145-151` (`bNeedEnable` and the
brake delay); `MoveTo()` on `bStartMove` (`:142-144`) and the automatic homing (`:152-157`) stay. Replace `:188`
(`bEnable := TRUE` on an accepted re-home) by nothing (`bHomeWanted`, one cycle later; `Home()` waits for `Ready` as
`HomePending`). Replace `:231` by `fbDriveEnable.RequestLock();` and `:259` by `fbDriveEnable.RequestLock();` (inside
the existing `IF NOT fbAxis.calibrated`).

Effect per issue: #111 the `rtHomed` lock request is dropped as soon as the follower wants the move (cycle N+1:
`bStartMove`/`bMoving`), and the drive was never disabled, so the move runs; if it was disabled anyway, `bMoving`

a move is wanted. #108 a pending move enables the drive; a stale one is cancelled. #114 (H1) the lock waits for
`StandStill`.

**Commit B: the follower's `bReady` and the stale-pending cancel** can be split out of A if Tim prefers smaller
commits (they are the two lines above); listed separately in the tests.

**Commit D (optional, Q4, #114 H2):** keep the far-switch bypass (`:209`) until the axis is at rest after a homing
